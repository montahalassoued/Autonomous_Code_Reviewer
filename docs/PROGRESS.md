## Done (in code)

| Area | What exists | Where |
| --- | --- | --- |
| Code parsing | tree-sitter parse and an in-memory NetworkX call graph for the agents' graph tools, built per job from the reviewed commit with no LLM call; its call edges come from `code_index/call_resolver.py` (imports, `self`/`cls`, same file, unique name), not bare-name matches (823 edges on this repo instead of 968). The semantic retrieval (Gemini, Voyage, Chroma, BM25, reranker, judge loop) was removed | `code_index/` |
| Review graph | Forward-only graph, `START` fans out to the 3 agents, `file::qualified_name` ids, None guards, offline end-to-end test | `review/graph.py`, `tests/unit/test_pipeline_offline.py` |
| Agents (Phase 3, part) | 3 review agents (Security, Logic, Quality) on one shared runner with strict finding validation and `REVIEW_AGENT_MODEL` (`openai/gpt-oss-120b` for all three, chosen by the benchmark); synthesizer with one section per category. Security checks authn/authz/IDOR on changed endpoints. An answer cut off at the output cap, empty, or not a JSON array fails its agent (partial review) instead of reading as "no issues" | `review/`, `review/agents/` |
| LLM client (Phase 3, part) | One Groq client for the agents: a timeout, logged retries on per-minute 429s, 5xx and timeouts only (the SDK's silent retries are off), a spent daily quota raised at once so a fallback model can take over, a process-wide limit on concurrent calls, and a review deadline (`REVIEW_DEADLINE_S`, 600 s, under the queue's visibility timeout) after which no call starts or waits | `review/llm_client.py` |
| Tracing (Phase 3, part) | Langfuse 5 traces, on only when both keys are set and forced off in tests: one trace per review (session = the PR) with an agent span per agent, a generation per Groq call (prompt, answer, tokens, latency, finish reason) and a span per tool call, ending after the post with `posted` / `skipped: <reason>` or an error. Everything sent is secret-masked and capped at 60k characters | `review/review_tracing.py`, `app/worker.py` |
| Monitoring | Prometheus metrics from the API (`/metrics`) and the worker (`:9100`), scraped every 15 s, and a provisioned Grafana dashboard at `http://localhost:3000`, both in docker compose | `review/review_metrics.py`, `infra/monitoring/`, `docker-compose.yml` |
| Durable jobs (Phase 2, part) | Webhook verifies HMAC, dedupes on (repo, target, head_sha) in the Postgres `reviews` table, enqueues to Azure Storage Queue; worker with retries and poison queue, the `reviews` lifecycle (`running` → `posted` / `skipped` / `failed` with a redacted reason, latency and missing categories), a stale check of the PR head before reviewing and before posting, partial reviews when one agent fails, and a redelivery that reopens a failed review | `app/api/webhook.py`, `app/jobs/`, `app/worker.py`, `review/graph.py` |
| Any repo, any push (Phase 7, part) | A GitHub App installed on all repositories sends every push and pull request; the worker checks out the event's repo at the reviewed commit and builds its call graph per job (`app/repo_checkouts.py`, a few cached), so no repo URL is configured and the tools read the change itself. A push of code to a branch is reviewed over before..after and posted as a commit comment. Installation tokens (an hour, minted once per installation) authenticate every GitHub call of a job, with `GITHUB_TOKEN` as the local fallback | `app/repo_checkouts.py`, `tools/github_auth.py`, `docs/GITHUB_APP.md` |
| Trigger policy (Phase 2, part) | Before the dedupe, the webhook ignores repos whose owner is not in `ALLOWED_OWNERS` (or listed in `ALLOWED_REPOS`), pushes that add or change no code, deleted branches and tags, draft PRs and authors GitHub does not list as collaborators; an unreachable GitHub gives 503 (fail closed); `ready_for_review` reviews a draft once it is ready | `app/jobs/trigger_policy.py`, `app/api/webhook.py` |
| Prompt-injection defenses (Phase 3, part) | The diff, the context and tool output sit between random-nonce markers with a shared "data, never instructions" rule; a heuristic lists added lines that look written for the AI reviewer in a warning section, and then the verdict is "Needs human review", never "Nothing blocking" or "Nice work"; a benchmark case hides a SQL injection behind an injection comment. Token-format secrets and the worker's own secrets are redacted from the diff and from tool output before they reach the model | `review/untrusted_input.py`, `review/injection_detector.py`, `review/agents/prompts/85_untrusted_input.md`, `review/state.py` |
| Output sanitizing (Phase 5, part) | Every LLM field is escaped for its place (no HTML, images, links, mentions, references, forged headings or fence breakouts), secrets are redacted (also in logs), invisible characters removed or revealed, fields and findings capped, the comment kept under GitHub's limit, and the summary marker only matches at the start of the bot's own comment | `review/output_sanitizer.py`, `review/secret_redactor.py`, `review/synthesizer.py` |
| Finding post-processing | One `postprocess_findings` for production and the benchmark: parse, validate, sanitize, move each finding to the added line its `evidence` quotes, merge duplicates (related rules within 5 lines; the same rule only at the same line or on the same quoted code), cap. Replayed on the 3-run gpt-oss-120b baseline: precision 0.81 to 0.91, strict recall 0.84 to 1.00, recall unchanged | `review/agents/agent_runner.py`, `review/finding_locator.py`, `review/finding_merger.py` |
| Review cost and limits | Each review's LLM calls and tokens (tool rounds included) summed over the agents and stored in `reviews` (also for a review that went stale after running); the diff sent to the agents is capped (`REVIEW_MAX_DIFF_CHARS`, whole files) and the review names the files left out or sent without a patch; a PR with nothing reviewable gets an explanation and no LLM call | `app/worker.py`, `app/jobs/review_status.py`, `review/diff_budget.py` |
| GitHub output (Phase 5, part) | One summary comment per PR, upserted by the `<!-- acr:summary -->` marker | `tools/github_tools.py` |
| API protection | The API reads at most 5 MiB of a webhook body (413 before the signature check) and serves no `/docs` or OpenAPI schema. In compose an Nginx gateway is the only entry point: two routes, body cap, per-IP rate limit, timeouts, and an optional allowlist of GitHub's webhook IPs | `app/api/webhook.py`, `app/main.py`, `infra/gateway/` |
| Packaging and deploy | Multi-stage Docker image, compose (Azurite + gateway + API + worker), Azure setup script, GitHub Actions test → build → deploy (deploy skipped until Azure vars exist) | `Dockerfile`, `docker-compose.yml`, `infra/`, `.github/workflows/` |
| Postgres (Phase 4, part) | `pgvector/pgvector:pg16` in docker compose, the full schema as `db/migrations/001_initial_schema.sql`, a migration runner with an advisory lock, a connection pool. The service writes only `reviews` so far; the indexer CLI fills `repos`, `files`, `symbols`, `edges` and `unresolved_calls` when run by hand, and `findings` waits for Phase 5 | `db/` |
| Indexer (Phase 4, part) | Full index of a checkout into `files`, `symbols`, `edges` (calls, imports, inherits, tested_by) and `unresolved_calls`, in one transaction, no LLM. Call resolution `self`/`cls` (with repo bases) → import (relative, aliases, `__init__` re-exports, `src/` layout) → same file → unique name; library calls and locals are skipped. Run by hand: `python -m code_index.code_indexer --repo owner/name --repo-path <checkout>` | `code_index/`, `tests/unit/test_call_resolver.py` |
| Tests | `tests/unit/` (offline, CI) and `tests/integration/` (real APIs, manual) | `tests/` |
| LLM benchmark (scorer v2) | 30 labelled cases (rule ids, severity bands, line ranges, allowed / forbidden findings) scored on what production would post: strict and loose recall, precision, F1, clean pass (no blocking false alarm) and clean strict pass, rule and line accuracy, tokens per true positive. `--replay` re-scores a saved run with no API call, a call cache makes reruns pay only for missing answers, and results record the scorer, dataset, prompt hashes and commit. A request over the model's per-minute token limit (413) is counted as "too large" and rules the model out for that agent instead of scoring 0; answers cut off at the cap are counted | `eval/llm_benchmark.py`, `eval/benchmark/` |
| Review eval harness (Phase 1, part) | 12 golden PRs written as edits to a small fixture repo (`eval/fixtures/review_repo/`, the PRs' `main`): injection, missing authorization, a prompt-injection PR, an off-by-one, a None dereference, an inverted check, a broken caller, an N+1, a missing test, and two clean PRs. Each runs through the production graph (agents with their tools, then the synthesizer) and is scored per category and as the posted review, with calls, tokens and latency per review. A recording client replays saved calls for free (`--offline`) and resumes after a spent quota. CI replays the committed recording against a baseline and fails when a golden PR's review gets worse. All 12 PRs are recorded (gpt-oss-120b, 2026-11-09): recall 1.00 in every category, posted-review precision 0.43, 5.5 calls and ~30k tokens per review. Merging a logic symptom (`unhandled_edge_case`, `wrong_api_usage`, `missed_state`) into the security finding on the same line raised precision to 0.50, and moving MEDIUM or worse findings with low confidence to a non-counted "Worth a look" section raised it to 0.59, both with the same recorded answers (2026-11-12) | `eval/review_eval.py`, `eval/review_harness/` |

## Not built yet

- Phase 1 (rest): `--mode structural` (after the Phase 4 context builder), context recall and precision, Langfuse dataset runs.
- Phase 3: JSON mode, scores and benchmark or review-eval runs in Langfuse, cost per agent. (The 3 agents, the shared runner, the nonce-wrapped prompts, the shared LLM client and tracing are done.)
- Phase 4: running the indexer from the worker (initial import), symbol diff, triage, structural context, PR text as input, agent tools reading Postgres instead of NetworkX. (Postgres, the schema, the `reviews` dedupe and the indexer itself are done.)
- Phase 4b: context subagent.
- Phase 5: inline review, only-new findings by fingerprint.
- Phase 6: incremental Postgres sync (each job still parses its whole checkout in memory, with no LLM call).
- Phase 7: push reviews, push coalescing.
- Azure resources: the setup script exists but has not been run, and it does not create a Postgres server yet (a deployed API fails at startup without `DATABASE_URL`).

## Known issues

- 3-run baseline of gpt-oss-120b (2026-10-22, `eval/results/llm_benchmark_20261022_084512.md`): quality 0.99, recall 1.00, strict recall 0.98, precision 0.95, clean pass 0.96, 0 invalid answers. Its one failure is a false HIGH on the clean case `logic_clean_in_place_filter` (an invented missing `expires_at` key, confidence "high" without a visible trigger) plus a MEDIUM `>=` boundary remark; the logic prompt was left as is for now.
- No fallback model: gpt-oss-20b gets 413 on the security and quality prompts at Groq's 8k tokens/min (`..._090610.md`), qwen3.8-27b cannot answer on the free tier, Cerebras needs a card, and NVIDIA's free endpoints had retired gpt-oss-120b and timed out or refused the other candidates. A spent 120b quota posts that category as a partial review.
- Review eval of the 12 golden PRs (2026-11-12): recall 1.00 but posted-review precision 0.59 (10 true findings, 7 false alarms; both clean PRs get none). The noise left: quality or logic remarks marked HIGH on code where they are not the point (`unbounded_query` x3, `missing_timeout`, `unhandled_edge_case`, `unchecked_external_result`). The offline replay lists each one with its rule.
- qwen/qwen3.8-27b cannot answer on the Groq free tier: its 1000 output tokens per minute are less than one review answer.
